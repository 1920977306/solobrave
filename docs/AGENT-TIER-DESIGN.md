## 1. 现状（设计落点全部核实过，不是猜的）

### 主系统侧（solobrave-server）
| 已有 | 说明 |
|---|---|
| `/api/tenants` | 平台超管租户面（仅 `is_platform_admin`） |

### 一个必须先钉死的概念区分
`bot_tenants.role` 是 **AI 助理人格**（达人助理/商务助理/商家助理）——它回答问题时扮演谁。
**代理是业务身份**（谁管谁、谁给谁充积分）——跟人格正交。
一个代理租户可以同时是"达人助理"人格（它自己也是达人）+ 代理身份（它名下有下级达人）。
⇒ **不许把代理做成 role 的第四个值**，否则人格和层级搅在一起，以后一个代理想换人格就动层级。

## 2. 概念模型

```
            SoloBrave 平台（admin / 商务助理）
           ┌──────────┴──────────┐
        代理A(团长)            代理B(团长)         ← agent_of = ''
        ├─ 达人1               ├─ 达人3            ← agent_of = 代理X
        └─ 达人2               └─ 达人4
```

- **商务（commerce）不是层级节点**——它是平台侧（或代理侧）的运营角色，帮平台/代理干活，不拥有下级。
- 达人是叶子（产品初期**不允许**达人再发展下级，见 D1）。
- 层级只影响三件事：①数据可见范围 ②积分来源（谁充给谁）③分佣归属（P2-C 后议）。

## 3. 数据模型变更（三个决策点）

### D1：层级深度 —— 单级还是多级树？
- 方案 a：只做一级（代理→达人），字段 `agent_of` 够用。
- 方案 b：**树结构存储（`agent_of` 自引用）、产品只开放一级**。
- **建议 b**：表结构按多级设计（零额外成本），产品层先限制"下级必须是纯达人"。以后放开"代理发展代理"不用改表、不用搬家。

### D2：代理身份怎么建模 —— 加列还是新表？
- 方案 a：`bot_tenants` 加列（轻量迁移，跟 role/weekly_sub 同模式，幂等 PRAGMA 检查）。
- 方案 b：新表 `bot_agent_tree`。
- **建议 a**：两列搞定， tenant 的所有现有读取函数（`get_active_tenants`/`get_tenant` 全是 `SELECT *`）自动带上，改动面最小：

```sql
ALTER TABLE bot_tenants ADD COLUMN agent_of      TEXT NOT NULL DEFAULT '';  -- 上级 tenant_key，''=平台直属
ALTER TABLE bot_tenants ADD COLUMN agent_enabled INTEGER NOT NULL DEFAULT 0; -- 0=纯达人 1=代理（有后台权限）
```

> ⚠️ 用 `agent_enabled` 而不是塞进 `status`——status 是租户生死（active/disabled），代理是业务能力，正交。

### D3：代理后台挂在哪 —— 主系统受限账号 vs bot 侧独立页？
- 方案 a：**代理 = 主系统一个受限账号**。复用刚做的权限管理页给代理账号开白名单（只看：下级达人/积分/商品；不能看：全平台/审计/设置）。代理登录主系统就是它的"代理管理后台"。
- 方案 b：bot 侧再做一个独立后台（像 7188 驾驶舱那样的 H5）。
- **建议 a**：主系统的 users/权限/积分中心都是现成的，再造一套就是第三套后台——正是老大说的"没有总台的样子"的反面。§119 的控制台已经是平台总台，代理视角是它的一个**数据范围裁剪**，不是新产品。

## 4. 权限矩阵（建议版，拍板后锁进守卫测试）

| 能力 | 平台 admin | 代理（受限账号） | 达人 |
|---|---|---|---|
| 看全平台租户总览 | ✅ | ❌ | ❌ |
| 看自己 subtree 的达人列表+数据 | ✅ | ✅（仅一级下级） | ❌ |
| 平台→任何人充积分 | ✅ | ❌ | ❌ |
| 代理→自己下级充积分（从代理余额扣） | ✅（代操作） | ✅ | ❌ |
| 看聊天审计 | ✅ | ✅（仅下级） | ❌（自己的） |
| 商品库/推品 | ✅ | ✅（推给下级） | 看自己相关的 |
| 改人格模板/角色 | ✅ | ❌ | ❌ |
| 升/降代理、绑下级 | ✅ | ❌ | ❌ |

**数据隔离判据（唯一入口）**：`subtree_keys(agent_tk)` = 一级下级的 tenant_key 集合。所有"代理视角"接口的第一道闸就是 `WHERE tenant_key IN subtree_keys(...)`——不许在各接口里手写过滤（§8.6 ③ 同款纪律：一个概念 N 个面，必须共用同一个函数）。

## 5. 改动清单（按 D1b/D2a/D3a 方案）

### bot 侧（daren_bot）
1. `db.py`：两列幂等迁移 + `subtree_keys()` / `is_agent()` helper + `transfer(from,to,amount)`（一个事务：from 减钱记正 cost 流水、to 加钱记负 cost 流水，from 余额不足抛 ValueError——照 `grant()` 模式）。
2. `admin.py`：`POST /admin/api/transfer` {from_key, to_key, amount}（校验 from 是代理、to 是 from 的直接下级）+ state 接口 tenants dict 带 `agent_of`/`agent_enabled`。
3. `handler.py`：积分不足话术顺带提示"找你的代理充值"（当租户有 agent_of 时）。

### server 侧（solobrave-server）
4. 控制台（feishu-console.html + `/api/feishu/console`）：租户卡加层级列（上级/下级数）+"设为代理 / 绑定上级 / 解绑"操作按钮（调 bot 新端点）。
5. 代理视角端点：`/api/feishu/console?as_agent=<tk>` 时数据裁剪到 subtree；积分中心加"转账"操作（代理出账）。
6. 权限管理页：内置"代理"角色模板（一键给账号开代理白名单）。

## 6. 分期

| 期 | 内容 | 量级 |
|---|---|---|
| **P2-A（数据+只读）** | 两列迁移 + transfer + 控制台层级展示/升降代理 | 小：纯数据变更+只读页，1 个 commit 量级 |
| P2-B（代理主动作） | 代理登录主系统看自己下级（数据/周报/消耗汇总）、给下级推品、积分转账 UI | 中 |
| P2-C（商务闭环） | 代理分佣结算（接 `bot_commission_pending` 已有表）、下级出单返利 | 大，**后议** |

> 建议先交付 P2-A：它让"达人升团长"在数据上真实存在、在控制台上可见可控——正是老大 18:25 要的最小闭环。P2-B 等第一个真代理出现再做（避免为想象的需求造后台）。

## 7. 风险与边界

1. **迁移幂等**：两列走 PRAGMA 检查 + ALTER 模式（与 role/weekly_sub 完全一致）；存量 3 租户（daren_boss/daren_test2/mumu）`agent_of=''`、`agent_enabled=0`，零数据搬迁。
2. **隔离唯一入口**：`subtree_keys()` 一处实现；守卫测试 = 代理视角接口断言"查不到别人 subtree 的租户"（负向对照必红）。
3. **转账原子性**：扣/加/两条流水必须一个事务；余额不足整体回滚（照 §8.11 两事务坑的教训）。
4. **人格/层级正交锁**：守卫测试 = `agent_enabled=1` 的租户 role 可以是任意值，代码不许假设"代理=某种人格"。
5. **不越界**：本设计不动 7188 驾驶舱（达人视图）、不动 bitable_sync、不动商品推荐链路。
