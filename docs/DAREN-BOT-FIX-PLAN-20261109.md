# daren_bot 修复方案（2026-11-09 周报问题清单 → 代码落地）

> 依据：《飞书助理聊天记录周度审查报告（2026-11-02 ~ 11-09）》。
> 本文档**纯方案，未动代码**。每条含根因定位（文件:行号，均已实读核实）与验收口径。
> 分两批：批 A = 周报点名的两条最高优先；批 B = 其余。每批动手前等老大拍板。

## 批 A（最高优先）

### A1. 抖音商品分享口令被误路由进视频拆解（P1，11-03 一天误伤 4 次）

**根因**（`handler.py:431-446`）：11-03 的短链修复只覆盖了「v.douyin.com 短链能解析出商品ID」的形态。商品分享口令（`【商品名…】复制此条消息打开抖音…【︽︽口令】 https://v.douyin.com/…`）走同一入口，`product_link.extract_product_id()` 对这类口令短链返回空（302 Location 不是商品参数形态）→ 掉进 `_route_video` → 扣 30 分 + failed。

**改法**：
1. `handler.py` 路由层在 `VIDEO_LINK_RE` 分支**之前**加商品分享文本特征识别：`复制此条消息打开抖音` / `【︽︽口令】` / `长按复制` / `￥`口令标记，命中即认定商品意图。
2. 命中后仍尝试 `extract_product_id` 解短链；解得出 → 正常商品链路；解不出 → 回「这个分享口令我解析不出商品ID，麻烦发商品链接或商品ID～」，**零扣费、不进视频拆解**。
3. `product_link.py` 补一条实测注释：口令短链的 Location 形态（修完用真实口令样本验证一次）。

**验收**：把 11-03 误伤的 4 条原始消息（含 mumu 17:08 那条）回放路由，全部进商品链路或零费提示；视频真链接仍走拆解。

### A2. QA 链路拿错账号档案（P1，同时污染真实用户和测试数据）

**根因**（`executors.py` QA 上下文构建 + `handler.py:_route_qa`）：QA 注入的账号档案默认取**本租户绑定账号**，用户消息里点名的其他抖音号（Wgg292 / Ayn11930）没有被优先取数；库里没有该号的采集数据时，不触发采集也不明说，直接拿绑定账号数据顶替回答。

**改法**：
1. QA 上下文构建时**先解析用户消息里点名的抖音号**（复用 `DOUYIN_IN_TEXT_RE`），点名了谁就用谁的档案。
2. 点名号的档案在库里不存在 → 明确回「TA 的数据我还没采集，把 TA 的抖音号单独发我，我采完再答」，**禁止用绑定账号顶替**。
3. QA prompt 加一条硬规则：回答引用的粉丝数/类目/成交数据必须来自被点名号的档案块，档案块没有就承认没有。

**验收**：回放 test2「Wgg292 能否带货」、t_20359bf4 两条冲突问答，回答不再引用萌萌超会买/旧档案数据；新号点名时给采集指引。

## 批 B

### B1. 「口播脚本」意图不承接、内容张冠李戴（P1，6 条消息才解决）

**根因**：没有「脚本生成」意图。达人要保温杯脚本，QA 链路拿占位模板（包里的话术）顶替；且已分析完的商品上下文没有绑定到脚本请求上，反复索要商品ID。

**改法**：
1. `product_intent.py` 加脚本意图识别（口播脚本/带货话术/前三秒钩子 等）。
2. `handler.py` 加 `_route_script`：命中后取**本轮/最近已确认的商品**（`db.has_recent_product_context` 已有同款机制，复用），带着商品分析块调 LLM 生成脚本；禁用占位模板，prompt 里写死「脚本必须基于给定商品的属性和卖点，不得套用其他品类模板」。
3. 没有商品上下文时才回要链接/ID（沿用 `NEED_PRODUCT_REF_REPLY`）。

**验收**：回放 mumu 11-04 保温杯链路：一次给对脚本，不出现「包」话术、不重复索要 ID。

### B2. 报抖音号求分析不触发采集、反复要截图（P1，新用户第一印象事故）

**根因**：待排查。「抖音名：一百 抖音账号：Ayn11930 帮我分析」按理走 `DOUYIN_IN_TEXT_RE → _route_douyin`，但回了「缺少可核验的账号数据」——该话术不在路由层，疑似掉进 QA 后被拒答兜底，或采集前置校验（昵称核验失败分支）话术错误。同一消息次日重发却正常。

**改法**：先加日志定位（回放该消息看实际走的分支），再按实因修。初步怀疑点：`_extract_name_hint` 把「这是我的账号帮我分析一下」整句当 name_hint 导致搜索核验失败 → 走「要截图」分支（与 B3 同源）。

**验收**：回放该消息 3 次，3 次都触发采集或给出一致的明确指引。

### B3. 报告标题把用户整句话当达人名（P2）

**根因**（`handler.py:198-207 _extract_name_hint`）：剥掉「抖音号：xxx」标注后，剩余的「分析一下这个账号呢」「跟我分析一下」等口语尾巴被当名字，`return t[:20]`。

**改法**：`_extract_name_hint` 加口语后缀剥离正则（分析一下.* / 帮我.* / 看看.* / 谢谢.* 等），只留昵称本体；剥离后长度不符合（<2 或全为动词短语）就返回空。

**验收**：回放周报两个实例（「CO师傅分析一下这个账号呢」「我的小号发给你跟我分析一下名称一百」），标题分别为「CO师傅」「一百」。

### B4. 周频限制话术自相矛盾 + 否认已有数据（P1）

**根因**：两处独立——① 周限闸门话术（`_route_douyin` 100分/周）与后续 QA 的「能分析」口径不一致；② QA 回答「没有可核实的商品记录」时未检索最近一期采集报告（11-02 明明有完整报告）。

**改法**：① 周限话术统一为「本周额度已用完，下周更新；加急找运营」，QA 侧不再出现「能分析」的矛盾承接；② QA 上下文构建时注入「最近一期采集报告摘要」块（周报同数据源），回答引用它而非否认。

**验收**：回放 mumu 11-07 15:08-15:25 五连问，口径一致且能答出「最近带的品」。

### B5. 兜底提示「没有附商品链接…」复读（P1）

**根因**（`executors.py:2615-2620`）：QA 回复尾部追加提示用的是**关键词启发式**（问题里含「视频/商品/链接/这条/这个品」就追加），不校验本轮上下文是否已处理商品输入。

**改法**：追加前检查本轮任务上下文是否已注入商品块/刚处理过商品输入（task 里已有现成字段），已处理则不追加；或把启发式收窄为「问题提到商品且本轮无商品块」。

**验收**：回放 11-03 14:46、11-04 15:37 两条实例，回复尾部不再出现该提示。

### B6. 半夜 auto 任务失败把「我再试一次就好」推给达人（P2）

**根因**（`failure_text.py:86/90` + worker auto 路径）：auto 任务（周报/排品）失败话术统一「我再试一次就好」，不分错误类型；409/登录态这类重试无效的错误也原样重试并推送，且凌晨主动打扰。

**改法**：① `failure_text.classify` 增补 409/登录态分类；登录态/409 → 话术「本周报告会延迟，运营处理中，不用管我」，**不重试、不推给达人**（只告警运营）；② auto 任务失败推送加时段闸门（23:00-08:00 只静默告警运营，不推达人）。

**验收**：模拟 409 与登录态失败，达人收不到「我再试一次」；凌晨失败无达人推送。

### B7. 内部词外泄「缓存命中」（P2，上轮已提未修）

**根因**（`handler.py:1058 / 1132 / 1166`）：进度文案直写「（结论缓存命中，秒出结果）」。

**改法**：达人可见文案去掉实现词，改「收到，这个之前分析过，直接给你结论～」；「缓存命中」仅保留在 admin/日志侧。

**验收**：复测同品二次发送，达人侧文案无「缓存」字样。

### B8. 纠错/投诉消息也扣 1 积分（P2）

**根因**（`_route_qa` 统一计费）：「分析错了」「为啥呢 什么原因」这类纠错/质疑消息掉进 QA 即扣 1 分。

**改法**：QA 路由前加纠错意图拦截（复用 `executors.py` challenge 检测的同款模式），命中走零成本兜底（已有「收到你的质疑…」话术在 `executors.py:2590-2606`），不扣费。

**验收**：回放「分析错了」，扣 0 分且收到质疑兜底话术。

### B9. 多图消息只分析第一张（复发）

**根因**：待排查 `_route_image`（`handler.py:991`）与 post 富文本解析（`handler.py:132 _parse_post`）的多图分支。

**改法**：先回放 11-03 14:37 双图消息确认是解析丢图还是路由只取首张；修解析后每张图独立出卡片。

**验收**：双图消息出 2 张卡片。

## 建议顺序

1. **批 A 两件（A1+A2）**：一天误伤 4 次 + 数据可信度，都是伤信任的，先修。
2. 批 B 按 B2/B3（新用户第一印象）→ B1/B4/B5（mumu 体验）→ B6/B7/B8/B9 排。

每批修完跑 `daren_bot/tools/` 下的 feishu_e2e / cache_probe 探针 + 全量回归，用周报里的原始消息做回放验收。
