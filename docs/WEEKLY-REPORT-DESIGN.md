## 0. 定位与边界（先把话说死）

- 主动推送走 **OpenAPI `im/v1/messages` + chat_id**（现有 `sender.send_text/send_image_path` 已走此路，ws 长连接只负责收事件，设计不碰 ws）。
- 我们是**周频采集，没有实时数据流**。"异常预警"= 周报里的一个 section，**不做**蝉妈妈式 7×24 实时推送，不过度设计。
- 周报是**留存权益**：内测期系统账免费，账先埋好，商业化时可无损切换为"付费版权益"。

## 1. 主动采集编排（核心新增，不是"一个定时触发器"）

**矛盾**：周报要"本周 vs 上周"，现有机制是达人发号才采——他不说话本周就没数据。
**解法**：新增 `weekly_scheduler` 线程（daren_bot 内 daemon），每周主动把绑定账号送入采集队列，达人零操作。

### 1.1 采集窗口与错峰
- 采集窗：**周日 20:00 → 周一 08:00**（百应低峰，避开达人白天使用时段）
- 错峰：`slot = int(hashlib.md5(tenant_key.encode()).hexdigest(), 16) % 720` 分钟，打散到 12 小时窗内，防止内测达人集中同一分钟打百应触发风控
- worker 采集器本身是单浏览器串行，天然限流；错峰防的是**入队堆积**

### 1.2 到点判定（每个订阅租户）
1. 无 `bind_douyin_id` 或未绑定 chat_id → 跳过
2. **本周已有该号成功采集**（`bot_collect_tasks` 本周内 type=douyin status=done）→ 跳过（达人自己发过就不重复采，省成本）
3. 入队：`enqueue_task(tk,'douyin',bind_id,0, chat_id=owner_chat_id, payload='{"auto":1}')`

### 1.3 失败重试与降级（设计硬要求）
- 自动采失败 → 窗内间隔 2 小时自动重排 1 次
- 二次失败 → **仍推送"数据缺失版周报"**（模板注明"本周采集未成功，附上最近一期数据"），绝不静默不发——静默一次，"每周陪伴"的信任就断了
- `need_login`（百应掉登录）→ 升级告警给运营（复用现有告警通路），同时发数据缺失版

### 1.4 首周冷启动
- 无上周基线 → 推送"**基线建立版**"周报（只列本周数据，无环比）
- **第一周异常预警不生效**，设计上明确，不造"上线即预警"的假象

## 2. 周报生成

新任务类型 `type='weekly_report'`，由采集完成事件链入队（worker.py 在 douyin 任务 done 且 payload.auto=1 时追加），或数据缺失版由 scheduler 超时兜底入队。

### 2.1 内容模块
| 模块 | 内容 | 数据来源 |
|---|---|---|
| ① 核心数据 | 粉丝 / GMV / 带货场次 / 口碑履约分 | 本周采集归档 |
| ② 环比变化 | 各项 vs 上周，↑↓ 带幅度 | 本周+上周归档 diff |
| ③ 异常 section | 命中的规则（见 §3），无命中则写"本周无异常" | 规则引擎 |
| ④ 下周建议 | 3 条以内，结合画像 | 1 次 kimi 32k 调用（≈1 次问答成本） |

### 2.2 交付形态
周报长图卡片（复用 `report_card.py` 视觉体系）+ 一句话摘要 + 完整文字版，与现有报告推送同形态。

## 3. 异常规则表（带场次上下文，宁漏勿滥）

**误报是信任生命线**。"GMV 环比降 20%" 不带上下文一定误报——达人这周没直播，GMV 降 90% 是正常。**规则必须带活跃门槛：**

| # | 规则 | 触发条件 | 上下文门槛（缺一不报） |
|---|---|---|---|
| R1 | GMV 异常下滑 | 环比降幅 >30% | 本周开播场次 ≥2 |
| R2 | 粉丝异动 | 环比涨 >50%（正向，疑似起量）或跌 >10%（掉粉） | 无（粉丝数周采可信） |
| R3 | 口碑/履约分下滑 | 降幅 >0.3 分 | 本周有成交 |
| R4 | 在售商品结构突变 | 在售商品数环比变化 >40% | 本周有成交 |
| 默认 | 本周未开播 | — | 不报异常，周报写"本周未开播，数据变化属正常波动" |

- 规则先**硬编码**（4+1 条常量），不做配置化后台——内测期没这个必要
- 原则：宁可漏报不可滥报，误报一次达人就觉得机器人不准

## 4. 独立计费路径（设计硬要求）

主动周采是真金白银的浏览器+kimi 成本，**绝不走达人 100 分扣费分支**（否则余额 0 的达人采不了，或达人质问"我没操作怎么每周扣 100 分"）。

- ledger 新增 action=**`weekly_auto_collect`**：cost 记 100（真实成本入账），`balance_after` 取当前余额**不变**，**不更新** `bot_credits_accounts`
- 实现：`db.py` 新增 `log_system_cost(conn, tenant_key, action, cost, ref_task_id)`，只写 ledger
- 商业化预留：将来"周报=付费版权益"只需调度器加一条判断 + 计费切 `deduct()`，表结构不动

## 5. 订阅管理

- `bot_tenants` 加列：`weekly_sub INTEGER DEFAULT 1`、`weekly_push_slot INTEGER DEFAULT 577`（周一 09:37，避开整点半点拥堵）
- 指令（意图分类新增一类，正则即可）：`取消订阅周报` / `订阅周报` / `周报`（查询订阅状态）
- 取消后 scheduler 跳过该租户；话术注明"随时发'订阅周报'恢复"
- 前提校验：该租户有 `owner_open_id` + 历史 chat_id（内测租户均满足；不满足的跳过并记日志）

## 6. 时序

```
周日20:00─周一08:00  weekly_scheduler（错峰slot到点）
        │ 本周未采过 & 已订阅 ?
        ▼
  enqueue type=douyin (credits=0, payload.auto=1)
        ▼
  worker 采集 ──失败──▶ 2h后重试1次 ──再败──▶ enqueue weekly_report(数据缺失版)
        │ done
        ▼
  worker.py: payload.auto=1 → enqueue type=weekly_report
        ▼
  weekly_report worker: 读本周+上周归档 → 规则引擎 → kimi生成建议(1次)
        ▼
  渲染周报卡片 → OpenAPI 推送 chat_id（长图+摘要+文字版）
        ▼
  bitable 同步本周数据（复用现有 sync）
```

## 8. 验收用例

1. 订阅租户到点自动入队，本周已采过的不重复采
2. 错峰：3 个租户 slot 分散 >60 分钟
3. 采集成功 → 周一 09:37 前收到周报卡（长图+摘要+文字版）
4. 首周（无上周数据）→ 收到基线版，无环比、无异常 section
5. 模拟"本周未开播+GMV 降 90%" → 周报写正常说明，**不**报 R1
6. 模拟"开播 3 场 GMV 降 35%" → R1 命中，周报异常 section 出现
7. 连续两次采集失败 → 收到数据缺失版周报（非静默）
8. ledger 出现 weekly_auto_collect 记录，tenant 余额不变
9. 发"取消订阅周报" → 下周不再收到；发"订阅周报"恢复
10. 积分 0 的租户照常收到周报（系统账路径验证）

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| 百应改版/掉登录导致整批失败 | 重试+数据缺失版+运营告警三连，不静默 |
| 内测达人增多后采集窗内跑不完 | slot 上限 720 分钟；超窗任务顺延到下周窗口并注明 |
| kimi 长文成本 | 建议模块限 3 条、max_tokens 2500，单周单达人 AI 成本≈1 次问答 |
