### 3. 真根因（本机复现，不是推测）

`79999` **超出 TCP 端口上限 65535**：

| 端口 | urllib 行为 |
|---|---|
| 79999 / 65536 | `gaierror [Errno 8] nodename nor servname provided, or not known` ← **与原始告警逐字一致** |
| 65535 / 9999 | `[Errno 61] Connection refused` |
| 7188 | `200` |

⇒ 原始告警里的「DNS 解析失败」**不是驾驶舱连不上**，是**探针写了个非法端口**（7188 少打一位）。
告警文案把「配置写错」说成了「驾驶舱异常」——老大被误导的地方正在这里。

### 4. 处置：把体检搬回本机（真值版探针）

`~/Developer/solobrave-ops/healthcheck.py` 新增 `cockpit_probe()`，接进已有 watchdog（launchd 每 120s）：

- 端口 `7188`（可用 `SB_COCKPIT_PORT` 覆盖），检查项沿用原名：`keys_ok` / `reach` / `http_200` / `form_anon_ok`
- `http_200` **带 k** 打 `/api/cockpit`（不带 k 必然 403 → 鉴权问题 ≠ 服务故障）
- **端口闸门**：越界直接判「端口非法」并拦下，不再伪装成网络故障
- **k 绝不进日志、绝不进告警文案**（k 等同访问密码）
- 告警走 healthcheck **既有通道**（飞书 webhook / Bark / 系统通知），30 分钟节流，与主服务/网关故障同一通道
- 回滚点：`healthcheck.py.bak-20261022-175319`

## 十三、团长端 vs 达人端（老大纠正）—— 达人数据走团长端，已落库

老大 2026-10-23 纠正：「**达人数据用团长端看，商品才会用达人端看**」。

### 1. 这条规则在代码里本来就有，是我探针跑偏了

| 端 | profile | 入口 | 干什么 |
|---|---|---|---|
| **团长端** | `data/buyin_browser/profile` | `buyin.jinritemai.com`（右上角身份=**团长**） | **达人数据**：达人详情页 概览/直播/视频/粉丝分析/**带货分析**/历史带货评价、达人广场、**合作达人管理**、**数据参谋** |

⚠️ **同一个 host、同一路径，用哪个 profile 就是哪个身份** ——
拿达人端 profile 打 `/dashboard/...` 会进「**达人自己的罗盘**」
（`compass_api/author/**`，author = 自己），看到的是「一白」的罗盘，
**不是**我们机构（团长）的数据。上一轮结论就栽在这儿。

### 2. 团长端真接口（页面上下文 fetch，**不需要 a_bogus**）

| 用途 | 接口 | 关键字段 |
|---|---|---|
| 机构经营概览 | `GET /ecom/captain/institution/statistics/overview?start_time=&end_time=&date_type=` | `business_info`: pay_gmv / settle_gmv / estimated_income_service_fee / real_income_service_fee / order_pay_num / avg_service_rate；`order_info`: order_daren_count / order_product_count / order_shop_count / avg_commission_rate；**`data_cutoff_time`（数据截止时间）** |
| **达人出单榜** | `GET /ecom/captain/institution/statistics/promoter/list?...&sort_type=0&sort_field=order_product_count&page=&page_size=20&promoter_type=0&author_query=&colonel_query=&date_type=1` | `promoter_infos[]`: name / **id(平台达人id)** / **user_source_id(真抖音号)** / order_product_count / order_pay_num / pay_gmv / settle_gmv / data_visible_status |
| 达人诊断 | `GET /ecom/captain/operate_analysis/coop_diagnosis/overview?period_type=&ewid=<机构id>` | gmv / daren_cnt / daren_average_gmv / captain_level / prod_date |

- `captain` = 团长、`institution` = 机构 ⇒ 路径名自证是团长视角。

  **不报错、直接返回空数组**（我第一次就踩了，以为「没数据」）。

### 3. 商品维度（老大确认归属后补上）

## 十四、两端能力矩阵（老大补充口径：团长端只查达人、达人端才查商品）

老大原话（第二句是**第一句的理由**）：

> 「商品数据在**达人端显示会更全面点**，因为会展示**这个商品前几位带好的达人卖的数据**
> 还有**那个视频**，团长端也可以找商品，但是**数据不会显示前几位达人的数据还有视频**，
> 所以我说**团长端只查找达人，达人端搜索商品**。」

⇒ 不是「哪端都行」，是**按「要什么数据」分工**。实测矩阵：

| 要什么 | 团长端 `profile` | 达人端 `profile_daren` |
|---|---|---|
| 达人档案 / 出单 / 成交 / GMV | ✅ 直连 fetch | — |
| 机构经营概览（支付GMV/订单量/成交达人） | ✅ 直连 fetch | — |
| 机构商品出单汇总（GMV/单量/带单达人数） | ✅ 直连 fetch | — |
| 商品基础信息（价/佣金/月销/类目/店铺/体验分） | ❌ | ✅ `material_list`（**需签名**） |
| 商品的带货达人数/浏览量/榜单/投千川标记 | ❌ | ✅ 选品库列表 |
| 商品诊断（风险提示/**30日动销达人数**） | ❌ | ✅ `/pc/diagnose/get_total`（**需签名**） |
| 商品相关直播 / 视频 / 相似达人 | ❌ | ✅ `/api/authorStatData/*`（**需签名**） |

### 达人端商品侧新挖到的接口

- 页面入口：`https://buyin.jinritemai.com/dashboard/product-diagnosis/home`（**商品质量诊断**）
- `/pc/diagnose/get_total?ewid=&product_ids=<逗号分隔平台商品ID>`
  → 商品诊断：**风险提示 / 30日动销达人数 / 诊断指标 / 佣金率**
- `/pc/selection_tool/promotion/list` + `/pc/selection_tool/promotion/pools`
  → **我的橱窗 / 最近带货 / 选品车**（达人端的商品来源池）
- `/api/authorStatData/productRelatedLives`（商品相关直播）、
  `/api/authorStatData/salesAnalyseV2`（带货分析）、
  `/api/authorStatData/authorRepresentWorksList`（达人代表作品/视频）、
  `/api/authorStatData/similarAuthor`（相似达人）、
  `/api/benchmark/product/deal`（商品成交对比）

### ⚠️ 关键约束：达人端接口**必须带页面签名**

- 裸 fetch（无 `a_bogus`/`verifyFp`）会被风控：
  `code=10001010A 当前环境存在风险` / `code=11001 当前网络不稳定`，
  **HTTP 200 但 data 为空**，极具误导性。
- ⇒ 达人端商品数据**只能在真实页面交互里抓**（我已验证真实交互能触发并抓到带签名的完整 URL）。
- 交互坑：商品诊断的勾选框是 **React 受控组件**（`<input class="auxo-checkbox-input">`），
  Playwright 的 `.check()` 报「Clicking the checkbox did not change its state」，
  要用 **JS 在外层 `.auxo-checkbox` 上派发完整鼠标事件序列**才选中。
- 对比：**团长端接口不需要签名**，页面上下文直接 fetch 就能出真数据（这一条是团长端更好用的原因）。

### 附带发现：达人端商品**列表层**就已经有老大说的那类数据
