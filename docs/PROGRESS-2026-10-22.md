### 3. 真根因（本机复现，不是推测）

`79999` **超出 TCP 端口上限 65535**：

| 端口 | urllib 行为 |
|---|---|
| 79999 / 65536 | `gaierror [Errno 8] nodename nor servname provided, or not known` ← **与原始告警逐字一致** |
| 65535 / 9999 | `[Errno 61] Connection refused` |
| 7188 | `200` |

⇒ 原始告警里的「DNS 解析失败」**不是驾驶舱连不上**，是**探针写了个非法端口**（7188 少打一位）。
告警文案把「配置写错」说成了「驾驶舱异常」——老大被误导的地方正在这里。

### 4. 处置：把体检搬回本机（真值版探针）

`~/Developer/solobrave-ops/healthcheck.py` 新增 `cockpit_probe()`，接进已有 watchdog（launchd 每 120s）：

- 端口 `7188`（可用 `SB_COCKPIT_PORT` 覆盖），检查项沿用原名：`keys_ok` / `reach` / `http_200` / `form_anon_ok`
- `http_200` **带 k** 打 `/api/cockpit`（不带 k 必然 403 → 鉴权问题 ≠ 服务故障）
- **端口闸门**：越界直接判「端口非法」并拦下，不再伪装成网络故障
- **k 绝不进日志、绝不进告警文案**（k 等同访问密码）
- 告警走 healthcheck **既有通道**（飞书 webhook / Bark / 系统通知），30 分钟节流，与主服务/网关故障同一通道
- 回滚点：`healthcheck.py.bak-20261022-175319`

## 十四、两端能力矩阵（老大补充口径：团长端只查达人、达人端才查商品）

## 二十一、排期必须落库（2026-10-24，老大「排品提醒没做」第二轮根因）

### 21.1 症状

修完入口（排品池真源 = 达人选品车）后，当天提醒**是对的**
（真推飞书 `pushed: 1`，文案「【一百 今天推这两件】」）。
但按老大的语义复查时发现：**明天会把一模一样的两个品再推一遍**。

### 21.2 根因：同一个算法两个消费者，只有一个落库

| 消费者 | 入口 | 落库 |
|---|---|---|
| 服务端 | `POST /api/deals/plan` | ✅ |
| 机器人 | `daren_bot.plan_notify.scan_and_push()` | ❌ 只算不写 |

⇒ `deals.scheduled_at` 永远是 0 ⇒ `build_schedule()` 里
「已有排期的保持原位」这条规则**从来没生效过** ⇒ 每天从头现算，
而 `base` 随日期平移 ⇒ **今天的坑位 = 明天的坑位**。

探针（会失败的那种）：`今天算出来的今天 == 明天算出来的明天` ⇒ `True`。

⚠️ 这个 bug **不报错、不掉日志、HTTP 200** ——
它是「安排」这件事在产品上**根本不存在**，不是「安排算错了」。

### 21.3 修法

1. `plan_notify.persist_plan()` —— 排期写回 `deals`。
2. `scan_and_push()` **先落库后推送**（`dry_run` 一个字都不写）：
   先落库 ⇒ 推送失败时排期已在、可重试；落库失败不阻断推送。
3. `build_schedule()` —— **过去日期的 slot 不接收新品**
   （落库后 `scheduled` 会带出过去排期并生成过去 slot，
   不拦的话新品会被排到已过去那天 ⇒ 永远推不出去）。
4. `requeue_overdue()` —— 排期停在过去 + **从没推过** ⇒ 清零重排
   （⚠️ 只认「从没推过」才补；已推过的不重复推，错挂比漏挂贵）。
5. `plan_text` 过滤过去日期。

### 21.4 顺手修掉的真 bug（我自己写出来的）

`persist_plan` 的 `executemany` 参数列序与 SQL 占位符错位
（`priority` 和 `plan_slot` 互换）⇒ **不报错**，只是
「坑位号」变成 58.6 这种分数。已加列序锁点断言。

### 21.5 ⚠️ 变异测试的 `.pyc` 陷阱（本次真踩）

「变异」与「还原」发生在**同一秒**且**文件等长**
（`if slots:` → `if False:`）⇒ Python `.pyc` 校验（mtime+size）判定缓存有效
⇒ **复用变异版字节码** ⇒ 「已还原」仍跑出变异结果，
一度误判「修复无效」。

⇒ 纪律：变异后 `sleep 1.2` 让 mtime 跨秒 + 清仓库自己的 `__pycache__`
（别清 venv，慢）。

### 21.6 验证（真实库）

- 真实扫描 `plan-scan dry_run=false` → `pushed: 0`（今天已推过，幂等生效）
  + `persisted: 2`（排期落库：`scheduled_at=1792771200`、`plan_slot=1/2`、

之前驾驶舱和服务端各写一份取数 SQL ⇒ 两个面各算各的。

⚠️ 为什么不直接 import `daren_cockpit.server`：那个模块**顶层就起
`ThreadPoolExecutor`** ⇒ bot 侧 import 会带起线程池 ⇒ 取数下沉到 `tools/`。

**② 飞书侧新链路**（`daren_bot/handler.py::_route_reco_query`）
